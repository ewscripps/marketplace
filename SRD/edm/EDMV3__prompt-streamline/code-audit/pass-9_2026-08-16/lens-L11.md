### Details

#### Finding 1 (P1, high): `update-patterns` reads `### ` headings that no audit report produces -- the Living Library has never captured a real finding and is now majority-polluted

- **What exists**: `cmd_update_patterns` is the sole mechanism by which the pattern library accumulates cross-initiative knowledge. It is called from four skills (`code-audit` step 9a, `audit-srd`, `audit-tickets`, `test-coverage`) and its output is read by the eleven lens agents and the four audit skills.
- **What it's wired to**: `bin/edm-state:5137` -- `grep '^### ' "$audit_report_path"`. The contract comment at `:4972-4975` states it plainly: "Extracts ### headings from the initiative's audit report."
- **What it should read**: the audit report's *finding titles*. Across all five report types this methodology actually produces, none of them are at `### `:
  - **code** (`code-audit/pass-*/REMEDIATION.md`, path resolved at `:5190`): `skills/code-audit/SKILL.md`'s own "Remediation Plan Format" puts finding titles at `##` (`## G1 (P1, L1+L4): [Title]`) and reserves `###` for the `Problem` / `Fix (concrete code or config)` / `Verification` / `Files` sub-blocks. On the round-8 report that actually shipped, the `###` set is the *document's structural scaffolding*: seven severity groupings under `## Findings Summary`, four `WORK ITEM N` blocks, five `Stage N` blocks under `## Rollout Order`, and six subsections under `## Verification Plan`.
  - **srd** (`audit-srd.md`), **ticket** (`tickets/audit.md`), **qc** (`qc/qc-summary.md`): zero `###` headings of any kind -- all four/five headings in each are `##`. Those three arms therefore record `new_findings: 0` on every run, permanently, and print `no novel findings to append` -- indistinguishable from a genuinely clean round. This is exactly the false-record ambiguity CA-355's fix eliminated one layer down (heading resolution) and which survives one layer up (extraction).
- **The live consequence is committed and visible**: `plugins/edm/docs/audit-patterns/code-audit.md:101-322` now holds **22** machine-appended `### ` entries, every one `source: EDMV3`, `date: 2026-08-16`, `status: pending-review`. Titles include `Syntax / static`, `Test suites`, `Lint / contract checks`, `Integration / manual smoke`, `Targeted re-audit (round 9)`, `Stage 0 -- Decision gate (blocks Stage 1; human required)`, `WORK ITEM 4 onward -- P2 detail`, `P0 (0)`, `P1 (9) -- fix before shipping`. They sit under `## Anti-Patterns` (heading at `:70`, section boundary `## Pre-Flight Checklist` at `:323`) alongside the five real hand-authored entries at `:72-96`. The library's largest section is now roughly 80 percent non-patterns, in a shipped plugin asset that thirteen prompt surfaces are pointed at as accumulated wisdom.
- **False Alarm Filter**: (1) fails -- `docs/audit-patterns/README.md`'s "Append Schema" (`:30-35`) specifies only the *destination* shape `### {Finding title} ({source-prefix}, {date}, {severity})`; the `###`-on-the-source-side rule is an undocumented implementation choice, and no SRD/ticket text mandates it. (2) fails -- the stop-word list at `:5126` (`summary|findings|recommendations|overview|appendix|legend`) shows the author anticipated structural leakage, but it is a six-string blocklist against an unbounded space and covers none of the 22 that landed, nor the documented template's own `Problem`/`Fix`/`Verification`/`Files`. (3) fails -- this is the only extractor.
- **Fix**: change the extraction to the heading level each report type actually uses for findings, per audit type, rather than one hardcoded `###`. For `code` that is `^## ` filtered to the finding-block shape (`## G{N} (...)` / `## CA-NNN`), excluding the fixed structural headings the Remediation Plan Format defines (`Context`, `Findings Summary`, `Detailed Findings`, `Decisions / Non-Findings`, `Rollout Order`, `Verification Plan`). For `srd`/`ticket`/`qc`, either point the extractor at those reports' real finding rows (they are tables, not headings -- which means a heading-based extractor cannot work at all for them and the arm should read the table) or make the three arms fail loudly rather than record `new_findings: 0`. Separately: revert the 22 polluted entries out of `docs/audit-patterns/code-audit.md` in the same commit, and add a wave7 case asserting that a synthetic report in each of the five formats yields the finding titles and *not* the structural headings -- the current coverage exercises insertion mechanics (CA-002, CA-056, CA-355) but never asserts *what* gets extracted.

#### Finding 4 (P2, medium; mode bit unverified -- no Bash this round): the commit hook's delegate reachability is unchecked, and failure is silent-clean

- **What exists**: `hooks.json:86` -- `command -v edm-lint-staged-artifacts >/dev/null 2>&1 || exit 0; edm-lint-staged-artifacts`.
- **The break**: `command -v` succeeds only for an *executable* file on PATH. If `bin/edm-lint-staged-artifacts` ever lacks its mode bit, the guard fires and the hook exits 0 -- which a PreToolUse hook interprets as "proceed", i.e. exactly the same signal as "commit is clean". Commit-time artifact lint stops enforcing with no diagnostic anywhere.
- **Nothing in the repository verifies the precondition**: `lint:bash-syntax` (`.gitlab-ci.yml:114`) and `lint:shellcheck` (`:252`) pass the file *as an argument* to `bash -n` / `shellcheck`, which need no execute bit. Every `T67 AC8` assertion (`wave7-smoke.sh:4708-4739`) `cat`s the file and greps substrings. `wave7-smoke.sh:2546` likewise. The only `-x` test in the entire `bin/tests/` tree is `:4570`, for `bin/tests/timing.sh`. And no test or CI job ever *runs* `edm-lint-staged-artifacts`, so there is no execution path that would incidentally catch it.
- **Why this is new**: before CA-436 the hook body was inline in `hooks.json`; the only executables it needed (`edm-state`, `edm-lint-artifacts`) were long-standing. The extraction added a brand-new file to the plugin's most privileged chain, and the guard that makes the hook degrade gracefully is the same guard that makes its absence invisible.
- **False Alarm Filter**: (3) partially applies -- the degrade-to-0 idiom is the consistent project pattern across all nine command hooks. What does not apply is the *unverified new dependency*: the other hooks' targets are covered by dozens of direct executions in the smoke suites; this one has none.
- **Fix**: add `[[ -x "${PLUGIN_DIR}/bin/edm-lint-staged-artifacts" ]]` to the T67 AC8 block (git tracks the mode bit, so this is a real regression guard), and ideally extend it to a loop over every `bin/` helper. Separately, give the delegate at least one behavioural case -- a scratch repo with a staged violating artifact asserting exit 2, and a clean one asserting exit 0 -- so the chain is exercised rather than only grepped.
