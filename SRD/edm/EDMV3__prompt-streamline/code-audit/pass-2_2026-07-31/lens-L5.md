## Findings (L5: Runtime Hygiene)

### CA-066 (P2, open, partially remediated): `evals/runs/` still has no retention policy

**Site**: `plugins/edm/evals/run-eval.sh:67`, `:201-202`; `plugins/edm/evals/README.md` (whole file); `.gitlab-ci.yml:196`.

The half of CA-066 that made the blocking gate misfire is **fixed**: `.gitlab-ci.yml:181-190` now measures `git ls-files -- plugins/edm/evals` (tracked bytes) instead of `du` over the working tree, so a local eval run no longer makes the local reproduction of the 100KB budget fail. The retention half is not. `run-eval.sh:201-202` mints `${OUT_ROOT}/${RUN_ID}` -- default `plugins/edm/evals/runs/<timestamp>_<git-sha>/` -- on every invocation, containing three full `claude -p` JSON payloads plus per-phase stderr logs, and nothing anywhere prunes. `evals/README.md` documents the run directory at `:33-36` and `--out DIR` at `:38-41` but states no retention rule and never tells the operator to delete anything; a grep for `retention|prune|delete|rm -rf` in that file returns nothing. The CI comment at `.gitlab-ci.yml:196` asserts the output is "retention-managed separately by CI artifacts", which is true of the pipeline artifact (`:560-564`, `expire_in: 30 days`) and of the runner's `GIT_CLEAN_FLAGS`, but says nothing about the developer laptop where the documented `bash plugins/edm/evals/run-eval.sh` invocation actually lands.

Correctly excluded from git (`plugins/edm/evals/runs/.gitignore:6-7` is `*` + `!.gitignore`), so this is disk accumulation only, not `git status` pollution -- which is why it stays P2 rather than rising.

**Fix**: prune to the N most recent run directories at the end of a successful run, and state the retention rule in `evals/README.md` next to the `--out DIR` paragraph.

### CA-104 (P1, new) -- FLAGGED FOR VERIFICATION, see orchestrator note below

**Site**: `plugins/edm/bin/edm-lint-artifacts:51-52`; `plugins/edm/bin/_edm-lint-lib.sh`.

```
SELF_DIR="$(cd "$(dirname "${BASH_SOURCE[0]:-$0}")" && pwd)"
source "${SELF_DIR}/_edm-lint-lib.sh"
```

`_edm-lint-lib.sh` exists on disk and holds `build_line_classes`, the awk fence/ignore-block classifier the linter cannot run without. It appears in this session's `git status` snapshot as `?? plugins/edm/bin/_edm-lint-lib.sh` -- untracked. There is no `.gitignore` pattern that would exclude it, so this is a missing `git add`, not an exclusion: the file was extracted from `edm-lint-artifacts` during remediation and the sibling edit to `edm-lint-artifacts` was staged while the new file was not. This repo's convention (`CLAUDE.md`: "Never use `git add -A` or `git add .` -- always stage files by explicit name") makes exactly this omission the standing failure mode.

Consequence on a fresh clone -- which is every CI runner and every plugin install: `source` fails, `set -euo pipefail` aborts at line 52, and every `edm-lint-artifacts` invocation exits non-zero before parsing an argument. That is the blocking `lint:artifacts` CI job (`.gitlab-ci.yml:85`), the `git commit` `PreToolUse` hook (`hooks/hooks.json:86`), `run-all.sh`, and the `--lint` / `--all-lint` / `--mermaid-ratio` timing modes.

Lens note: the *cause* is packaging rather than runtime file creation, so L7/L8 may co-own it; it is reported here because it is an untracked file in `git status` on the deployment host, and because the coordinator asked this lens to confirm no stray untracked artifacts remain in the tree.

**Verification / fix**: `git ls-files --error-unmatch plugins/edm/bin/_edm-lint-lib.sh`; if it exits 1, `git add plugins/edm/bin/_edm-lint-lib.sh` before the remediation commit. Add the file to the `bin/` inventory table in `plugins/edm/CLAUDE.md` and to `lint:bash-syntax`'s glob so it cannot silently drop out again.

**Orchestrator verification (added post-report)**: `git ls-files --error-unmatch plugins/edm/bin/_edm-lint-lib.sh` exits 0 -- the file IS tracked (committed in 6ddcf0c). The lens had no Bash tool and reasoned from a stale pre-commit `git status` snapshot rather than live state, exactly the caveat it flagged in its own "Not traced" section. ## Noted / Not Actionable

- **CA-104 as originally filed is stale**: `_edm-lint-lib.sh` is tracked in the current tree (see orchestrator verification above). Not re-investigated unless it goes untracked again.
- **The flock lock file is still never unlinked (`bin/edm-state:830`)** -- REMEDIATION.md's CA-029 prescribed `rm -f "${lockfile}"` after the FD scope closes and it was not applied. Correctly so: unlinking a flock file after release is a classic mutual-exclusion bug -- a second process that has already opened the old inode ends up holding a lock on a file that no longer has a name, and a third process creates a fresh inode and locks nothing. Leaving the zero-byte file in place is the standard idiom. With `.gitignore:10` now matching, the finding's real consequence is gone. Worth one comment line at `:829` recording that the non-unlink is deliberate, so round 3 does not "fix" it.
