## Judgement: is `EDMV4-T17 AC2` the defect, or the library's behaviour under a missing dependency?

**The assertion is the defect.** The library's degradation contract is correct and is proven
independently elsewhere: `edm-state:73` guards the source with `[[ -r ... ]] &&`, and every consumer
guards each call with `declare -f edm_marker_path` (`_edm_marker_write:91`,
`_edm_marker_remove_if_matches:113`, `cmd_session_start:4598`, `cmd_update_patterns:6090`), so a
vanished library degrades to a silent no-op rather than a failure under `set -euo pipefail`.
`edm-gateguard:88-95` does the same and exits 0. There is no observable behaviour of the library
under a mid-flight disappearance that needs changing.

The current AC2 body does not in fact delete the shared library -- it copies `edm-state` into a
scratch `bin/` and omits it (wave8-smoke.sh:349-355) -- so the specific hostility three agents hit
has already been fixed. What survives is the same class one level up: the assertion still compares
two samples of `edm-state validate EDMV4` against the LIVE initiative, taken at two different times
and from two different working directories, and treats any difference as evidence about the
library. `validate` legitimately flips between 0 and 3 whenever a concurrent `record-partial-verdict`
or `audit-round-start` changes `OPEN_PARTIALS`/`OPEN_AUDIT_ROUND` -- which is exactly what a
parallel wave does. That is L3-012, and the fix is to make the assertion's own inputs private and
symmetric, not to change the library.
