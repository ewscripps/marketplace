# Key Decisions

| # | Decision | Chosen | Rationale | Date |
|---|----------|--------|-----------|------|
| D1 | How to run a roughly 8-file patch-level bug fix | **`lifecycle_mode=fix-pack`** -- tickets generated directly from `analysis.md`; Phases 1, 2, 3 and 5 recorded skipped; a single Gate 3 ticket-pack review replaces the Gate 2 -> Phase 4 -> Gate 3 sequence; no convergence gate required to archive | Full six-phase on a fix this size would cost more than the bug. EDM's own qualification table puts a 1-3 file bug fix outside EDM entirely; at 13 files this sits just inside, and fix-pack is the mode the matrix defines for exactly this shape. The single gate is the only review this initiative gets, which is why the pack was reviewed against the analysis rather than waved through | 2026-08-31 |
| D2 | Gate 3 -- the VERIF ticket pack (11 tickets, one epic, 2 XS / 7 S / 2 M, AC 10-12 each, DAG acyclic) | **Approved** | Ordering is encoded in the DAG rather than prose: `VERIF-T09` (raise `maxTurns` 25 -> 50) depends on `VERIF-T08`, so the budget raise cannot land before the sentinel work. That ordering is load-bearing -- a higher budget makes truncation rarer and therefore harder to notice, which is strictly worse for diagnosis than the status quo if it lands first | 2026-08-31 |
| D3 | `edm-ticket-writer` added a 14th file beyond the analysis's 13: `bin/edm-check-verifier-sentinel`, rather than embedding the sentinel check as prose in `skills/implement/SKILL.md` | **Accepted** | Acceptance item 4 requires a negative test that fails if the check is removed. Prose inside a `SKILL.md` cannot be executed, mutated or asserted against, so that test would itself have been "an assertion that does not prove what it claims" -- the exact defect class this initiative exists to fix. Precedent is CA-436, where the inline `PreToolUse` hook one-liner was extracted into `bin/edm-lint-staged-artifacts` for the same reason. Adds no binary beyond `bash`/`grep`/`sed`/`tail` | 2026-08-31 |
| D4 | Seven tickets edit agent prompt text, and "the agent reliably emits the sentinel" is not statically verifiable | **No AC asserts model behavior.** ACs assert instead that the instruction exists and is unambiguous about the final-line requirement (grep-verifiable), and that the consumer refuses input lacking it (fixture-verifiable) | An AC of the form "the agent reliably emits X" would sit PARTIAL forever with no runtime environment able to close it, land in `partial_verdict_map`, and hard-block archive under D15. The resulting architecture is also simply better: **the prompt asks, the consumer refuses, and only the second half has to be reliable.** The fix does not depend on model compliance | 2026-08-31 |
| D5 | The VERIF branch was cut from the EDMV4 branch, which was 3 commits behind `origin/main`, so it carried plugin version `3.2.0` and `VERIF-T11` would have set `3.2.2` from the wrong base | **Merge `origin/main` into the VERIF branch before implementation.** Done: branch is now level with `origin/main` at `3.2.1`. Closes the EDMV4 D4 residual as a side effect. Required first committing the 315 staged EDMV2/EDMV3 archival renames as their own commit, because `origin/main` still holds those files at their pre-archive paths and git refuses to merge over staged changes to them | Setting `3.2.2` from a `3.2.0` base would have conflicted on the version line at merge to main. `VERIF-T11`'s ACs were already pinned to the end state (jq reads `3.2.2` from both manifests) so they held either way, but the base still had to be right for the diff to be honest | 2026-08-31 |
| D6 | **Defect found on `origin/main` while fixing the version base: the 3.2.1 release shipped with its two manifests out of sync.** `plugins/edm/.claude-plugin/plugin.json` reads `3.2.1`; the registry `.claude-plugin/marketplace.json` still reads `3.2.0`, last bumped at `42b5115` for the 3.2.0 release | **Folded into `VERIF-T11`'s scope**: T11 ships `3.2.2` to BOTH manifests and closes the existing 3.2.1 drift in the same change | The marketplace manifest is the registry consumers install from, so advertising `3.2.0` while the plugin declares `3.2.1` makes update detection unreliable -- consistent with the observed behavior in this session, where a first `/plugin` reported "already at the latest version (3.2.0)" and only a second invocation pulled 3.2.1. This is the same two-places-to-update class of defect EDMV4's audit found in the SRD's constraints table, and it is why `VERIF-T11`'s ACs compare both manifests programmatically via `jq` rather than by eye | 2026-08-31 |

| D7 | The shipped sentinel grammar is a three-field superset of what the epic specifies. `analysis.md` and the ticket ACs say `<!-- {MARKER}-COMPLETE range={ASSIGNMENT} audited={N} -->`; the implementation ships `range={ASSIGNMENT} assigned={M} audited={N}` | **The three-field grammar is correct and is what shipped.** Recorded here because the QC audit correctly flagged (P2) that it was applied consistently across all four emitters, all four consumers, `CLAUDE.md` and the checker -- and recorded in no decision row until now | The two-field form's short-count check was **not computable**. It compared `audited=` against "the count implied by `range=`", but `range=` is documented to accept a section group or a lane name as well as a ticket span, and no integer is derivable from `sections-1-5` or `lane-b`. As written, only the QC ticket-range form could implement the check; T05/T06/T07 would have had to invent per-verifier range parsing or silently drop it -- losing the clean-but-incomplete case, which is the more interesting half of the contract. `assigned={M}` makes it a plain integer comparison for all four markers. Caught during T01 review, before any consumer was written | 2026-08-31 |
| D8 | The `assigned={M}` field introduced in D7 was initially made **authoritative over** the dispatcher-supplied `[expected-count]` argument, so a truncated agent emitting `range=T01-T08 assigned=1 audited=1` passed the check it was subject to (QC audit P1, reproduced at exit 0 in both paths) | **Precedence inverted to a trust ordering**: `[expected-count]` (dispatcher) outranks the `range=` span, which outranks `assigned=`; where the latter two disagree the larger wins. Fixed in `42a0671` | The two artifact-derived values come from the agent being policed and cannot be trusted against the exact failure the check exists to catch -- the artifact was able to defeat its own gate. The defect was introduced by D7's own fix: making the comparison a pure integer check also made an agent-supplied number authoritative, and the trust model went backwards with the simplification. Worth recording as the initiative's own instance of the class it was built to close | 2026-08-31 |
